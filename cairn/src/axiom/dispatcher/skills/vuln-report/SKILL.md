## 去重检查（上报前必做）

上报前 MUST 先查询已有漏洞列表，检查是否已有相同漏洞：

```bash
curl -s "${AXIOM_SERVER}/projects/${PROJECT_ID}/vulns" | python3 -c "
import sys, json
vulns = json.load(sys.stdin)
for v in vulns:
    print(v.get('id',''), v.get('title',''), v.get('status',''))
"
```

如果已有漏洞的标题与你要上报的漏洞描述**同一根因**，不要重复上报。不同表现但同一根因算一个漏洞。

## 漏洞 vs 发现 — 判断标准

**发现不等于漏洞。** 上报前必须通过以下判断：

### 通用判断树

```
是否成功构造并发送了攻击 payload？
  └── 否 → 发现，写入 fact，不上报
是否有响应证明危害真实发生？
  └── 否 → 发现，写入 fact，不上报
危害是否超出了攻击者的合法权限？
  └── 否 → 不是漏洞（在自己的权限内用自己的资源操作）
是否有完整证据链（payload + 响应 + 影响量化）？
  └── 否 → 标 severity: "info"，status: "pending"
全部满足 → 按下方流程上报
```

### 按漏洞类型的判断标准

#### IDOR / 越权
- **必须证明**：用攻击者 token 访问了/修改了/删除了**不属于攻击者**的资源
- **不够**：接口没报错、返回了 status:1 — 必须确认返回的数据属于其他用户
- **测试方法**：最好有两个账号，A 的资源 B 能访问才算 IDOR。单账号环境下，用枚举到的 ID 查询，响应中 uid/owner 不等于自己才算确认
- **常见误报**：用自己的 file_id 设为头像（不是别人的）、查自己的订单详情（不是别人的）

#### 优惠券/支付类业务逻辑
- **必须证明**：获得了**不该获得的折扣/商品/资金**，或绕过了**真实的限制**
- **不算漏洞**：
  - 在自己的订单里用自己的有效优惠券（无论在哪个步骤传入）
  - 取消订单后优惠券恢复（这是正常业务逻辑）
  - preCalculate 不锁定价格（preCalculate 是前端预览，不是安全控制）
- **算漏洞**：
  - 用别人的优惠券下单（IDOR）
  - 同一张券并发用于多个订单且都生效（竞态，不是串行取消重用）
  - 篡改券面值参数（5 元券当 50 元用）
  - 0 元或负金额下单

#### 限购/库存绕过
- **必须证明**：实际创建了超出限制的订单且能正常履约
- **不算漏洞**：参数被接受但订单最终被拦截
- **算漏洞**：限购 1 件但实际成功购买了 N 件，且订单状态正常

#### 暴力破解/速率限制
- **必须证明**：实际破解成功（命中正确 OTP/密码，账号被劫持）
- **不算漏洞**：发了 N 次失败请求没被限速 — 这只是观察，不是漏洞
- **算漏洞**：在 OTP 有效期内成功遍历出正确验证码，完成了账号绑定更换
- **如果无法完成完整破解**（如 OTP 有效期太短），上报 status: "pending"，severity: "high"，注明"已验证无速率限制但未完成完整破解"

#### 竞态条件
- **必须证明**：并发请求导致了不正常状态（重复扣减、重复领取、超额创建）
- **不算漏洞**：串行操作产生的正常行为
- **测试方法**：用并发工具（xargs -P、parallel curl）同时发多个请求

#### 加密缺陷
- **必须证明**：实际解密了他人的密文，或恢复了密钥并验证
- **不算漏洞**：发现用了固定 IV/ECB 模式 — 这是观察
- **算漏洞**：用已知明文恢复了密钥，解密了其他用户的手机号/身份证号

#### 文件上传
- **必须证明**：上传了不该能上传的文件类型，或未授权上传成功并造成危害
- **不算漏洞**：需要 token 才能上传（无论 token 在 header 还是 body）
- **算漏洞**：完全不需要任何认证即可上传、上传了可执行文件并被服务端执行

## 用法

```bash
curl -X POST "${AXIOM_SERVER}/projects/${PROJECT_ID}/vulns" \
  -H "Content-Type: application/json" \
  -d '{
    "title": "SQL 注入 - /api/search 可读取全量用户数据",
    "description": "参数 keyword 存在时间盲注。使用 payload admin'\'' OR 1=1-- 成功绕过登录，确认可读取 users 表全部 1.2 万行数据。",
    "prerequisites": "需要目标系统使用 MySQL 数据库且 keyword 参数未做参数化处理。",
    "impact": "攻击者可通过注入读取数据库中所有用户数据，包括密码哈希、手机号、身份证号。",
    "evidence": [
      "【正常请求】curl -X POST https://target/api/search -d \"keyword=test\" → HTTP 200, {\"results\": []}",
      "【攻击 payload】curl -X POST https://target/api/search -d \"keyword=admin' OR 1=1--\" → HTTP 200, {\"results\": [...全量数据...]}",
      "【影响验证】sqlmap 确认 users 表可读取，共计 12431 行"
    ],
    "reproduction_steps": [
      "1. 访问 /api/search?keyword=test 观察正常响应",
      "2. 注入 payload: admin'\'' OR 1=1--",
      "3. 响应返回所有用户数据，确认注入存在",
      "4. sqlmap 验证数据库级别影响"
    ],
    "status": "confirmed",
    "source": "explore",
    "reported_by": "worker-name"
  }'
```

## evidence 规范

每条 evidence 必须包含：

1. **攻击前状态** — 正常请求与响应
2. **攻击 payload** — 完整的 curl 命令或原始请求
3. **攻击后结果** — 响应原文片段，证明漏洞存在
4. **影响量化** — 读取了多少条数据 / 影响了哪个用户 / 获取了什么权限
