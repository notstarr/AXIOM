# Reason 场景策略：自动增量规划

这是 AXIOM 代码为 `fact_batch`、`low_watermark` 或 `max_wait` 触发的 ReasonRun 固定注入的场景策略。你不能自行选择其它 Reason 子提示词；统一合同以主提示词为准。

本轮不是历史总结，也不是重新建立全局计划，而是针对当前目标重新寻找可执行的覆盖缺口，并消费增量决定哪些方向需要继续执行。

**禁止直接执行漏洞验证和探索**

## 增量处理重点

1. 先逐个读取本轮新 Fact，并通过 `graph.json` 找到该 Fact 对应的前置产物（`source_artifact_ids` 中的 `findings.md` 与 `leads.md`），没有来源关系的推测不能伪装成新方向。
2. **综合研判与独立裁量**：
   - `findings.md`（已确认事实）是最高权重的定性依据,是派发 Intent 的第一来源；
   - `leads.md`（未决线索与后续方向）必须完整读取，但是否采纳并派发新 Intent 根据业务价值与目标差距独立研判决定：
3. 判断新 Fact 是否带来了材料性变化。下列算材料性，应延续同一棵树而不是新开主题：
   - 新的拼装函数、子路径、无登录 URL、鉴权头。
   - 列表响应里新出现的对象 id / token / secret 字段。
   - 自己的对象 200、别人的对象也 200（或隔壁树 403、本树 200）。
   - 写入被服务端忽略的字段（例如客户端传 `enabled=0` 实际仍启用）。
   - 无登录入口只验了状态码，尚未证明业务副作用。
   新页面标题、版本号、WAF 指纹、缺安全头，不算材料性。
4. 建立当前攻击面状态表时，按能力树归类，不要按单条 URL：已真实验证、已确认不存在或未部署、具体外部阻塞、仍未验证。一棵树只测了 GET，写/触发/密钥字段仍算“仍未验证”。
5. `fact_batch` 重点处理新事实批次；`low_watermark` 重点补充即将耗尽的、尚未验证的高价值方向；`max_wait` 处理等待过久但仍有明确可执行路径的 Fact，并顺带评估快照中尚未评估的已结束 Intent。快照中的 unassessed Intent 无论触发原因是什么都必须在本轮完成一次性评估（每个 Intent 只调用一次 `axiom reason intent assess`）。触发原因只决定优先级，不决定是否结束规划。
6. 充分检查已有开放、失败、取消和已完成 Intent，复用可延续的 Todo，避免同义或相同目标重复派发。单次工具失败、没有新 Fact、只验证了一小批接口或队列暂时为空，都不能直接证明攻击面已穷尽。
7. 对每个仍有未验证材料性方向、未知参数/对象、部分完成链路或可执行替代路径的 Todo，继续派发高价值、独立、可执行、非重复的 Intent；队列为空时，从未完成 Todo、历史 Leads、失败/取消 Intent 和业务全景中寻找下一条攻击链。新 id 来自上一轮列表响应时，应派“用该 id 继续本树”，不要另起一个“发现新任务 id”的 Todo。
8. 当`A`todo是`B`todo的前置条件时，优先完成`A`,然后使用`A`提供的前置信息，继续派发`B`下的intent(全图联想，攻击链串并联)
9. 当尝试过以上操作仍无可派发的intent/todo，且无正在运行的intent时，读全图以启发新的攻击面

不要因为达到批量阈值或低水位就机械凑数，也不要因本轮只看到增量 Fact 就忽略当前目标范围内已有的未完成业务链。触发原因只是优先级提示，不是结束理由。
