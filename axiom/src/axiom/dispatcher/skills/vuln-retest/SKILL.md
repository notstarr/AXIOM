# 漏洞复测方法

复测回答的问题只有一个：**这条漏洞现在是否仍然成立。**

## 一、适用与不适用

| 场景 | 用什么 |
|---|---|
| 漏洞已上报（任意状态），要判断「现在还成不成立」 | **本 Skill** |
| 第一次判定一条上报是否成立、要不要定档 | 审核的方法论 |
| 红队成果的复核与计分 | 红队方法论 |

复测不是审核。审核产出的是裁决与结论（要不要认、算不算重复、等级对不对）；复测产出的是**二选一加一个逃生口**：还成立 / 已修复 / 无法判定。

## 二、复测不做的事

- 不重新定档：等级、类型、受影响资产、标题一律不碰。觉得定错了，在理由里写一句，交给人工。
- 不改描述：描述、前提、影响、修复建议、复现结构都不改。复测改描述等于把被检验的对象换掉。
- 不改状态：漏洞的「待验证 / 已验证 / 忽略 / 重复」不由复测决定。
- 不做重复判定：判重需要比较全任务的历史，那是审核的活。

## 三、三态判定门槛

三态互斥，必须选一个。**门槛写死，不要凭感觉放宽。**

### `exists` —— 仍然成立

必须同时满足：

1. 本轮**亲手发出请求**并拿到回包（不是看旧截图、不是引上报记录）；
2. 仍能拿到与上报**同等性质**的结果：越权读到他人数据、未授权访问到功能、非法输入被服务端接受、凭据可换出等；
3. 至少一个**对照**排除了替代解释：不是缓存、不是公开数据、不是你恰好用了管理员身份、不是前端假象。

只证明「接口还通」不算成立。通而拿不到越权结果，可能已经修复了。

### `fixed` —— 已修复

必须同时满足：

1. 本轮无法再复现原有结果；
2. 能指出**拒绝发生的位置**：401/403/404、服务端归属校验报错、参数被过滤或归一、接口下线、凭据失效且确认是修复方收掉的；
3. 拒绝不是因为你用错了身份、打错了地址、漏了必需的 header。

**以下都不算 `fixed`**：连接超时、DNS 失败、502/504、通用 500 报错、被 WAF 拦在门口而看不见业务响应、测试账号登不上而你又没有别的账号。这些是「没验证到」，属于 `inconclusive`。

### `inconclusive` —— 无法判定

出现以下任一情况就选它，并写清楚卡在哪：

- 目标不可达（下线、DNS 变了、只在内网可达而你进不去）；
- 账号不可得：测试账号被删/改密/锁号，且没有第二个可用身份；
- 被风控或 WAF 拦截，看不到业务层的真实响应；
- 依赖的第三方、支付、消息通道不可用，导致链路走不完；
- 本轮观察同时支持两种解释，且没有成本合理的方法区分它们。

`inconclusive` 不是失败，是诚实。猜一个 `exists` 或 `fixed` 会让下游拿着错结论去返工或去交付。

## 四、证据下限

- **至少 1 张 `kind=packet` 的报文图**，证明本轮真的发出了请求、真的拿到了回包。不要求每步一张——复测不是逐步举证，是对一个命题的一次检验。
- 一步里有多个报文时，截**能证明结论的那一张**。
- 报文图记录的是「这一步发生过」；业务效果图（`kind=business`）只是可读性补充，不计入下限。
- 截图里出现 Cookie/Token 可以接受，不要为了打码把身份遮掉。
- 结论要能被别人照着重放：把关键请求行、关键 header、关键响应字段写进理由。

## 五、账号基线重建（复测特有）

上报到复测之间，目标侧经常已经变过：

| 变化 | 处理 |
|---|---|
| 口令被改、会话过期 | 重新登录，不复用旧 Cookie/Token |
| 角色被收 | 记录「原角色已不可得」，换可用身份做同类验证；做不到就 `inconclusive` |
| 测试账号被删 | 按需重新注册；注册不了就 `inconclusive` |
| 接口路径或参数变了 | 按当前前端/接口重新定位入口，不要死磕旧报文 |

开跑前先做一次**身份自检**：用一个只有目标角色能进的页面或接口确认「我现在确实是低权限」。

**不要用管理员身份顺手验证一遍**——那会把「管理员本来就能做」当成漏洞仍然成立，是复测最常见的假阳性。

## 六、写操作边界

- 只在 `{run_dir}` 内写临时文件（请求体、截图）。
- 判断成立所必需的写操作才做；能读到同样结论就别写。
- 真做了写操作（建单、改配置、上传），把创建的对象、时间、是否清理写进结论。
- 禁止：批量删除、批量改状态、落 webshell、上传持久化文件、对生产做压测。

## 七、输出

```bash
axiom review retest submit exists       --reason "..."
axiom review retest submit fixed        --reason "..."
axiom review retest submit inconclusive --reason "..."
```

理由结构（1-3 句，中文）：

```text
本轮做了什么 → 看到什么（关键状态码/字段） → 与上报的差异或一致 → 剩下的不确定点
```

不写修复建议（那是报告的事），不写定级意见。

## 八、提交前自查

- [ ] 本轮真的亲手发过请求，不是复述上报内容？
- [ ] 有对照，且对照排除了「自己有特权」「数据本来就是公开的」？
- [ ] 至少一张 `kind=packet` 报文图，`axiom review status` 已 `ready`？
- [ ] 结论只用了三态之一？
- [ ] 理由指向证据（状态码、字段、响应差异），而不是推测？
- [ ] 没有调用任何改状态、改描述、写报告的接口？

## 九、安全边界

- 严守 Task Scope 与 Guard，不越界、不扩大攻击面、不横向。
- 只围绕这一条漏洞的核心声明验证；发现的新问题记进理由里提示人工，不要顺手扩大验证。
- 无法安全验证时停止，选 `inconclusive` 并写清阻塞。
