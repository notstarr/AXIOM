# 漏洞审核方法

本 Skill 供 Reviewer Worker 使用。审核目标是判断现有漏洞声明是否被 Finding 和 Evidence 直接支撑，而不是重做一轮完整 Explore。

## 核心顺序

1. 先读取 `review_target.json`，确认标题、类型、严重程度、受影响目标、利用前提与影响是否自洽。
2. 完整读取 Finding，再逐个读取 Evidence。必须能把每个核心结论对应到具体请求、响应、工具输出或可重现的现象。
3. 查看同 Task 的未归档漏洞列表，优先识别同根因、同对象、同利用条件的重复上报。
4. 仅当现有证据无法区分真伪，且可在 Scope 内用低风险、最小请求完成时，才做最小复测。
5. 将审核过程、支持材料、反证、不确定性与最终裁决写入 `artifacts/review.md`。

## 裁决标准

### verified

- Finding 与 Evidence 能直接证明漏洞存在；
- 受影响对象、利用前提和影响范围没有被证据明显夸大；
- 不是已有更早漏洞的同根因重复。

### duplicate

- 必须指向同 Task 中更早、未归档的漏洞；
- 不能仅因标题相似就判重复；
- 应说明共享的根因、受影响对象和证据重合点。

### ignored

- 证据不支持声明、现象属于预期行为、明确超出 Scope，或缺少安全影响；
- 原因必须可审计，不得只写“无效”或“忽略”。

### needs-human

- 关键证据缺失、必须使用不可获得的身份/环境，或复测风险超出 Reviewer 允许边界；
- 必须写明缺失材料、无法自动裁决的原因和人工下一步。

## 最小复测边界

- 严格遵守 Task Scope、Guard 和现有凭证边界。
- 优先重放已有请求或执行只读校验；禁止扩大扫描、批量枚举或引入新攻击面。
- 禁止破坏性操作、持久化、社工、拒绝服务或越出 Scope 的第三方访问。
- 新产生的原始证据放入 `evidence/**`，不得把长响应或密钥复制进漏洞正文。

Reviewer 只提交结构化裁决和审核 Artifact；不创建 Fact、Todo 或 Intent，不改写漏洞的标题、描述、等级、影响或修复建议。
