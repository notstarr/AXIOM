# `needs-human` 审核附件示例

> 本文件展示如何明确记录阻塞条件和未知维度，而不是含糊地写“建议人工复核”。

# 漏洞审核记录

## 1. 审核对象与原始声明

- 漏洞：`v030`——普通商户可修改其他商户的结算银行卡
- 目标：`POST https://target.example/api/settlement/bank-account/update`
- 原始声明：替换 `merchant_id` 可跨商户修改银行卡。
- 候选裁决：`needs-human`

## 2. 已读取材料

- Finding：`artifact:a300`
- Evidence：`artifact:a301`，仅有一段请求文本，没有成功响应、修改前后状态或第二商户截图。
- 当前凭证库只有商户 A；没有商户 B 的授权测试身份。

## 3. 独立验证与关键对照

已执行的安全步骤：

1. 使用商户 A 读取自己的结算账户摘要，确认当前测试对象；
2. 将请求中的 `merchant_id` 改为不存在的测试值，但不提交真实银行卡数据，服务端返回通用 `400`；
3. 检查是否存在只读预览或 dry-run 接口，未发现；
4. 未向任何真实商户 ID 提交更新，因为该操作可能改变结算去向，具有不可逆财务风险。

无法建立有效对照：缺少商户 B 的授权身份和专用测试银行卡，也没有可验证的沙箱环境。旧 Evidence 不足以证明服务端最终状态被跨商户修改。

## 4. CVSS v4.0 风格维度核查

| 维度 | 结论 | 阻塞或证据 |
|---|---|---|
| AV | Network | 已确认 HTTPS API 入口 |
| AC | Unknown | 不知道是否还有服务端风控条件 |
| AT | Unknown | 可能要求特定结算状态或已审核银行卡 |
| PR | Low（暂定） | 原声明使用普通商户，但缺少第二商户对照 |
| UI | None（暂定） | 请求看似直接提交，未证明是否需后续审批 |
| VC | Unknown | 本轮未证明读取他人银行卡信息 |
| VI | Unknown，潜在 High | 未证明服务端最终状态被跨商户修改 |
| VA | None/Unknown | 原声明未涉及可用性 |
| SC/SI/SA | Unknown | 若影响支付系统可能存在后续影响，但无证据 |

关键指标未知，不能生成可信 CVSS Vector，也不能据潜在财务影响直接判 `verified`。

## 5. 实际安全影响与边界

当前只能证明存在一个接受 `merchant_id` 的更新端点，不能证明该参数决定最终授权对象，也不能证明跨商户状态变化。

## 6. 历史重复判断

存在更早的商户资料读取越权 `v014`，但它是只读资料接口，根因和完整性影响均未证明相同，不能贸然判重复。

## 7. 裁决与理由

裁决：`needs-human`。

```bash
axiom review decision submit needs-human --reason "已验证端点和本人账户基线，但缺少第二商户授权身份、测试银行卡与可撤销沙箱；真实提交可能改变结算去向。AC/AT及VI等关键维度未知，现有Evidence没有服务端修改后状态，无法安全裁决为已验证或忽略。"
```

## 8. 不确定性及人工下一步

人工复核需要：

1. 提供两个已授权的沙箱商户身份；
2. 提供专用测试银行卡和可恢复的结算状态；
3. 记录商户 B 修改前后服务端状态；
4. 比较商户 A 修改本人、修改商户 B、无效商户 ID 三组结果；
5. 确认是否存在审批流或支付系统后续影响。
