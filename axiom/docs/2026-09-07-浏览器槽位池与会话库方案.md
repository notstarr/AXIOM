# AXIOM 浏览器槽位池与会话库方案

## 背景

现有方案（见 `2026-08-04-原生AI浏览器与Lease隔离.md`）实现了 Lease 级**页面所有权**隔离，但浏览器本体始终是"一只实例 + 一个共享默认上下文"。随着多 Intent 并发成为常态，暴露出四类问题（2026-09-07 任务 t_197 复盘 + 外部评审交叉验证）：

1. **共享 cookie jar**：所有租约绑定 `browser.contexts[0]`（browser_broker.py:588），Intent 之间身份互染——A 清 Cookie / 触发登出会波及 B，也无法做无缓存对照；
2. **执行窗被租约等待侵蚀**：浏览器就绪等待发生在 Pi 进程拉起之前（pi.py:385），实打实消耗 `execute_timeout_seconds`，重派 Intent 出现系统性"零发包收口"；
3. **登录态不可控**：SecTest Profile 手工登录一次永久生效，无版本、无多身份、无法按任务重置；
4. **运行期打扰**：headful 窗口常驻屏幕、抢占焦点；且进程级故障时无自动重建（2026-09-07 实锤：系统 Chrome 152 与 Playwright CDP 协议不兼容导致全部 `browser_*` 工具不可用，broker 复用坏实例使故障固化）。

产品诉求：**任务开始前人工登录一次 → 多 Intent 并发复用同一登录态 → 运行期零打扰 → 并发稳定**。

## 现状还原（证据）

```text
Runner 内 Browser Broker（单 AF_UNIX 服务，单 asyncio 事件循环）
→ 单只浏览器：优先 Chrome for Testing（chromium-1228/1223 硬编码），
  缺失时回退系统 Chrome（browser_broker.py:604-629，回退不告警）
→ connect_over_cdp(9223) 后取 contexts[0] 作为唯一工作上下文（:588）
→ Lease 仅隔离 Page 所有权（_rebind_pages），Cookie/Storage 全局共享
→ cd p_mismatch：一个 Runner 绑死一个 CDP 地址（:562-566）
→ CDP 存活且属 SecTest Profile 即复用，不校验浏览器版本兼容性
```

实测：单只 CfT（1 个空白页）= 12 进程 / 1.4 GB RSS。

## 目标架构

```text
┌ 登录阶段（仅一次，用户主动发起，允许打扰） ┐      ┌ 运行阶段（headless，零打扰） ┐
│ 控制台任务详情 →「准备会话」               │      │ CfT 单实例 --headless=new     │
│ → Broker 唤起临时 headful 登录窗          │ 完成 │ Slot0 ← ctx ← 注入会话快照 S  │
│ → 用户在窗口内登录目标站                   │ ───▶ │ Slot1 ← ctx ← 注入会话快照 S  │
│ → 导出 storage_state → 存项目会话库        │      │ Slot2 ← ctx ← 注入会话快照 S  │
│ → 关窗；快照含 HttpOnly Cookie/LocalStorage│      │ （独立 cookie jar，互不污染）  │
└──────────────────────────────────────────┘      └──────────────────────────────┘
```

### 1. 槽位池（Slot Pool）

- `BrowserSlot = {slot_id, mode, state, context, lease, session_ref}`，容量可配（context 模式默认 4）；
- `register_lease` 分配空闲槽位：无空闲则排队，等待走**独立计时**（`browser_slot_wait_seconds`，默认 120s），不消耗执行窗；
- 槽位初始化二选一：
  - **快照槽位（默认）**：`browser.new_context(storage_state=快照)`——干净环境 + 登录态注入，租约结束销毁；
  - **persistent 槽位（兼容/兜底）**：绑定既有 SecTest 默认上下文，沿用现行为；同一时刻至多 1 个（全局串行），用于单 session 强制站点与过渡期；
- `close_lease`：快照槽位销毁上下文回池；persistent 槽位仅清理页面。

### 2. 会话库（Session Store）

- 新表 `browser_sessions(id, project_id, name, storage_key, content_hash, origin_summary, cookie_count, created_at, updated_at)`；`storage_state` JSON 本体入 FileStore，DB 存 key + hash；
- 写入：登录模式导出 / 新增 `browser_save_session` 工具（worker 主动固化会话）/ 存量 SecTest Profile 一次性导入脚本；
- 读取：任务执行配置新增 `browser_session_id`（Reason 派发 Intent 时随租约下发，`execution_input` 增加字段）；未指定则该租约申请干净槽位；
- 凭证安全口径不变：`redact_headers` 默认脱敏，明文需显式 `include_sensitive=true`。

### 3. 登录模式（会话准备流程）

- `POST /api/v1/tasks/{id}/browser/sessions/prepare` → Broker 起临时 headful CfT（独立临时 Profile，不碰 SecTest）；
- 用户手动登录 → 控制台点「完成」（或 `confirm` API）→ 导出 storage_state 存库 → 关窗；
- 全程仅此窗口可见，运行期再无任何有头窗口。

### 4. 护栏

| 护栏 | 默认值 | 行为 |
|---|---|---|
| 槽位并发上限 | 4（instance 模式 2） | 超出排队（独立计时） |
| 单槽位页面限额 | 8 页 | `browser_open_page` 超限报 `slot_page_limit` |
| 空闲回收 | 10 分钟 | 关闭 context；租约下次操作重建并重注入快照 |
| 崩溃自愈 | — | `browser disconnected` → 清空槽位 → 活跃租约标记 retryable → 走既有 `TransientWorkerError` 重试；重试时按会话库重建 |

### 5. 模式开关与 headless

- `AXIOM_BROWSER_MODE = context（默认）| instance`；
- `instance` 模式：每槽位独立 CfT 进程（独立临时 Profile + CDP 端口 9240+，支持任务级 `--proxy-server` 出口隔离），供代理出口/极端抗干扰需求按任务开启；
- headless：`AXIOM_CHROME_HEADLESS` 统一收口（默认 on，`--headless=new`）；登录模式窗口强制有头；任务级可退回有头+最小化（现 `_minimize_only_if_already_minimized`）对抗 headless 指纹识别。

### 6. 时序修正

浏览器槽位获取整体前移且独立计时；Pi 进程启动后才起算 `execute_timeout_seconds`。等待不再吃执行窗。

## 与现有方案对比

| 维度 | 现状 | 槽位池方案 |
|---|---|---|
| 浏览器实例 | 1 只，二进制自动回退（失败静默） | 1 只 CfT 常驻 headless；二进制缺失硬失败并告警 |
| 会话模型 | 全局共享 `contexts[0]`，Cookie 全局共享 | per-lease context + 会话库快照注入；persistent 槽位兼容旧行为 |
| Intent 并发 | 页面级并发、身份互染，同站多身份不可行 | 槽位上限内真并发，身份互不相染 |
| 登录态 | SecTest Profile 手工登录，永久生效、不可版本化 | 显式快照：可登录一次多处复用、可重建、可多身份、可按项目隔离 |
| 干净对照组 | 无 | 快照槽位天然干净；不注入即为全新环境 |
| 运行期打扰 | headful 常驻、抢焦点 | headless 零打扰；仅登录模式主动唤起 |
| 零发包收口 | 租约等待烧执行窗 | 槽位等待独立计时 |
| 故障域 | 崩溃后持续复用坏实例（t_197 实锤） | 断连感知 → 重启 → 按快照重建（秒级自愈） |
| 出口代理 | 不支持 | instance 模式按任务支持 |
| Worker 工具面 | 20 个 `browser_*` | **完全不变**（+可选 `browser_save_session`） |
| 凭证安全 | 默认脱敏 | 不变；快照文件 600 权限落 FileStore |
| 资源（4 并发） | 1.5 GB（串行复用） | ~2.5 GB（4 context 增量）；instance 模式 ~6 GB（逃生舱） |

## 兼容与迁移

- `browser_*` 工具 Schema、`page_id`/Ref 规则、网络/Console 游标读取**全部不变**，Worker 与 Pi Extension 零改动；
- 存量 SecTest Profile 登录态：提供一次性导出脚本转为会话库快照，迁移期可继续用 persistent 槽位；
- 单 session 强制站点（新登录踢旧会话）：任务级 fallback 到 persistent 槽位（退回串行，保正确性）；
- `cdp_mismatch` 语义保留；`instance` 模式下放宽为"槽位各自的 CDP 地址"。

## 风险与回滚

| 风险 | 缓解 |
|---|---|
| storage_state 快照过期（目标站 token 轮换） | credential-refresh 打通；租约内 `browser_get_credentials` 现场刷新；快照带 `updated_at` 供 Intent 判断新鲜度 |
| headless 被 WAF 指纹识别 | 任务级退回有头+最小化；UA/视口/时区 per-context 可配 |
| 多 context 内存压力 | 槽位上限 + 空闲回收；超限排队不拒答 |
| 快照注入与站点风控冲突（多 session 副本被识别） | 任务级 persistent 串行 fallback |
| 回滚 | 槽位池开关切回单 context 模式（保留现路径为一个"容量=1 的 persistent 池"），一个版本内可随时退 |

## 实施拆解（每阶段独立可合入）

1. **阶段一：槽位池 + 护栏 + headless**（稳定性主线，~2–3 天）
   Broker 重构为槽位池；per-lease context；并发上限/页面限额/空闲回收/崩溃自愈；headless 开关与二进制缺失硬失败；persistent fallback。
   验收：4 Intent 并发浏览器操作互不染 Cookie；杀浏览器进程后租约自动重建；现有全部测试绿 + 新增槽位池单测/并发测试。
2. **阶段二：会话库 + 登录模式**（体验主线，~2 天）
   `browser_sessions` 表 + FileStore 快照；prepare/confirm API；`execution_input.browser_session_id` 传递链；存量 Profile 导入脚本。
   验收：登录一次 → 4 Intent 并发复用同一登录态，操作互不影响；会话快照可重建。
3. **阶段三：时序修正 + 动作直播**（~1–2 天）
   槽位等待独立计时；Broker page/network 事件 → activity 上报 → 控制台实时流。
   验收：排队等待不再缩短执行窗；控制台可见 Intent 的浏览器动作与流量摘要。

## 验证口径

- 单测：槽位分配/回收/限额/崩溃重建；快照注入与导出 round-trip；persistent 槽位互斥。
- 集成：双 Intent 并发对同一目标站操作，断言各自 Cookie jar 独立、网络捕获按槽位隔离。
- 回归：现有 763 用例全绿；`test_pi_adapter` 浏览器相关断言不回退。
