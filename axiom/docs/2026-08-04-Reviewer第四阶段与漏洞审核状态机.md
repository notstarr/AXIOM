# Reviewer 第四阶段与漏洞审核状态机

日期：2026-08-04

## 目标

AXIOM 新增第四个逻辑 Worker：Reviewer。它在漏洞及 Finding/Evidence 正式持久化后执行独立审核，
不阻塞 Task Goal 主链，也不创建 Fact、Todo 或 Intent。

```text
Bootstrap / Reason / Explore / Reviewer
```

Reviewer 可裁决：

```text
verified / duplicate / ignored / needs-human
```

分别映射为漏洞状态：

```text
已验证 / 重复 / 忽略 / 待验证
```

## ReviewRun

`vulnerability_review_runs` 保存独立状态、Lease、Worker、预算、重试、活动、输入指纹、裁决和重复目标。

```text
pending → claimed → running → concluding → completed
                    └──────────────→ failed / cancelled
```

约束：

- 同一漏洞最多一个活动 ReviewRun；
- Explore 漏洞在 Explore Artifact 与漏洞原子落库的同一事务排队；
- 人工创建的待验证漏洞立即排队；
- 历史未归档、非只读 Task 的待验证漏洞由迁移 `20260804_0034` 补队列；
- 关键漏洞字段（含修复建议）、Finding 或 Evidence 变化会取消旧 Lease、恢复待验证并创建新 ReviewRun；
- 直接归档正在使用的 Finding/Evidence Artifact 同样会取消审核；恢复该 Artifact 后，待验证漏洞重新排队；
- 人工直接设置终态会取消活动 ReviewRun；
- `needs-human` 不自动循环排队，人工可显式“重新审核”。

Reviewer 可在 Task `running/stopped/completed/failed` 时作为后处理运行，不受 Task 运行截止时间影响。
它共享全局并发、模型后端容量和 Task Worker Pool，每个 Task 同时最多一个审核。Task 暂停不取消
Reviewer；漏洞归档会取消审核，恢复仍为待验证的漏洞会重新排队。调度时有可领取主链工作的 Task
整体优先；同一 Task 内也始终先领取 Bootstrap、Reason 和 Explore，再用剩余容量领取 Reviewer。

## Prompt、Context 与能力

阶段 Prompt：

```text
src/axiom/dispatcher/prompts/review.md
src/axiom/dispatcher/prompts/review_conclude.md
```

方法 Skill：

```text
src/axiom/dispatcher/skills/vuln-review/SKILL.md
```

`whatisvul` 继续锁定为全阶段 Skill；`vuln-review` 默认只绑定 Reviewer，但仍是可分配 Skill，不是
Reviewer 的硬依赖。人工解除绑定后，Prompt 会继续使用内置审核原则，不会因找不到该 Skill 失败。

Reviewer Context 使用普通 Manifest，并额外生成：

```text
review_target.json
```

其中包含唯一审核目标、完整漏洞字段、Finding/Evidence 元数据和受控本地 `content_path`。普通
`hints.json`、`knowledge.json`、`vulnerabilities.json`、图谱、Todo 和 Artifact 索引继续可读，用于 Scope、
业务规则、重复判断和来源追溯。

固定内置操作：

```text
read / write / edit / bash
axiom skill path/doctor
axiom credential list/get/refresh
axiom review status
axiom review decision submit
```

Skill、具体 MCP Tool 和扩展 Tool 可通过 Worker 能力抽屉单独分配给 Reviewer。`common` 现在表示四阶段
全部生效；新 Lease 才读取最新能力快照。

## 审核边界

Reviewer 将现有 Finding/Evidence 作为待验证线索，而不是默认可信结论。目标可达、Scope 允许且操作安全时，默认必须执行至少一次新的独立验证，并增加一个只改变关键变量的对照。`verified` 原则上需要本 ReviewRun 的新鲜复现；判断 `ignored` 前也必须实际复现并记录反证、无安全影响的对照，或说明完整直接静态证据为何已足够。缺少身份、环境或安全复测条件时使用 `needs-human`，不能只根据文件下终态结论。

### CVSS 维度与四状态附件

`vuln-review/SKILL.md` 已按 CVSS v4.0 Base Metrics 风格重构，要求逐项核查：

```text
AV / AC / AT / PR / UI
VC / VI / VA
SC / SI / SA
```

这些维度用于校准利用条件、安全边界和实际 C/I/A 影响，不作为自动评分器。未知维度必须写明缺失的
身份、环境或证据；只有全部 Base Metrics 都有依据时才允许附参考 Vector。Reviewer 不修改漏洞原始等级。

Skill 附件提供四份完整审核记录示例：

```text
references/verified-example.md
references/duplicate-example.md
references/ignored-example.md
references/needs-human-example.md
```

Reviewer 形成候选状态后必须读取对应附件；若在两个状态间犹豫则读取两份。附件只规定结构、证据粒度和
裁决门槛，禁止复制示例对象或结论。

结构化命令：

```bash
axiom review decision submit verified --reason "..."
axiom review decision submit duplicate --duplicate-of v001 --reason "..."
axiom review decision submit ignored --reason "..."
axiom review decision submit needs-human --reason "..."
```

所有决定必须填写审核原因。重复目标必须属于同一 Task、未归档且早于当前漏洞。

Reviewer 只能更新漏洞状态、状态原因和重复引用；禁止改写标题、类型、等级、描述、利用前提、影响、
修复建议、目标或原始 Evidence。Reviewer 不创建 Fact、Todo、Intent，不调用 Reason/Explore 专属操作，
完成后也不自动触发 Reason。

## Artifact 与完成协议

必填：

```text
{run_dir}/artifacts/review.md
```

可选：

```text
{run_dir}/artifacts/evidence/**
```

正式类型：

```text
review.report
review.evidence
```

Artifact 使用 `review_run_id` 所有者并保存到 `tasks/{task}/reviews/{review_run}/`。文件中心按 ReviewRun
建立独立文件夹；Review Evidence 会作为正式 Evidence 关联目标漏洞。漏洞最多关联 20 个 Evidence，
`axiom review status` 会在本轮新证据超过剩余容量时拒绝就绪，要求先删除多余文件。

Reviewer 最终文本严格为 `FINISH`。Runner 同时校验结构化裁决和非空 `review.md`；缺失时在同一 JSON
Pi Session 中有界收口。Reviewer 不使用 Explore 的 FINISH 格式归一化或核心文件兜底。

## API 与前端

人类接口：

```text
GET  /tasks/{task_id}/vulnerabilities/{vulnerability_id}/reviews
POST /tasks/{task_id}/vulnerabilities/{vulnerability_id}/reviews
GET  /tasks/{task_id}/vulnerability-review-runs/{review_run_id}
```

Dispatcher 另提供 ReviewRun 的 claim/start/input/heartbeat/activity/status/decision/conclude/complete/release
和 Token Usage 内部接口。

漏洞详情展示审核状态、Worker、触发来源、审核时间、决定、原因、重复漏洞蓝链和 Review Artifact，并提供
人工重审。外部预览保持可用；正式外部 submit/retry 只接受 `已验证` 漏洞，服务端拒绝重复、忽略和待验证。
